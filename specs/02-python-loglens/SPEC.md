# LogLens — Log Analysis CLI & Library

**Version**: 1.0.0
**Stack**: Python 3.11+, packaged CLI (`loglens`), typer + pydantic v2, pytest
**Audience**: AI coding agents evaluated on building a production-quality Python CLI + library.

---

## 1. Overview & Goals

Build **LogLens**, a CLI tool that ingests application logs (JSON-lines and plain-text formats), normalizes them into a common event model, detects anomalies with a rule engine, and produces an actionable report — terminal, JSON, or a self-contained HTML file.

**Why this exists.** This project grades an agent's ability to:
- Design a clean library core with a thin CLI shell (importable, testable).
- Write robust parsing with graceful degradation over dirty real-world-ish data.
- Implement an extensible rule/plugin architecture.
- Handle files, streams, glob patterns, and malformed input without crashing.
- Produce artifacts (JSON/HTML reports) with correct Python packaging and ≥ 75% coverage.

**LOC expectation.** ~2,000–3,000 lines of Python (package + tests don't count toward the target). A single `main.py` blob fails the architecture gate.

## 2. Success criterion (pass/fail)

ALL of the following must be true:

1. **Sandboxed** — no network access required; sample logs are generated by the tool itself (`loglens sample` writes demo log files).
2. **Ready to run** — from clean checkout: `pip install -e ".[dev]"` then `loglens --help` works. No services, no config files required.
3. **All tests pass** via `pytest`, and **line coverage ≥ 75%** of the `loglens/` package.
4. **CLI contract holds** — every command below works exactly as specified (`--help` documents it).

## 3. Architecture (REQUIRED — deviations = fail)

```
loglens/
├── pyproject.toml          # PEP 621; entry point: loglens = "loglens.cli:app"
├── loglens/
│   ├── __init__.py
│   ├── cli/                # typer app; arg parsing + output formatting ONLY
│   ├── models/             # pydantic models: LogEvent, Incident, Report, RuleConfig
│   ├── parsers/            # JSONLinesParser, PlainTextParser, format auto-detection
│   ├── rules/              # Rule protocol + built-in rules + registry
│   ├── engine/             # normalization pipeline, correlation windowing, scoring
│   ├── reporters/          # terminal (rich), JSON, HTML (Jinja2 template, self-contained)
│   ├── io/                 # readers: file, glob set, stdin, with encoding/failure policy
│   └── samplegen/          # `loglens sample` — writes realistic demo logs
├── tests/                  # pytest; unit + CLI (typer CliRunner) integration
└── README.md
```

Rules:
- `cli/` contains **no** business logic; it delegates to `engine/` and formats results.
- Parsers, rules, and reporters are **plugins registered in registries**; adding one = one class + one registration line.
- The library is importable without the CLI: `from loglens import Engine, JsonLinesParser` works in a REPL.
- Time is injected (`clock` callable) so rules are testable deterministically.
- `loglens/io/readers.py` yields events lazily (generators) — a 1 GB file must stream, not load (grader may test with a generated 100 MB file).

## 4. Event model

Normalized `LogEvent`: `timestamp` (UTC, tz-aware), `level` (`DEBUG|INFO|WARNING|ERROR|CRITICAL`), `message`, `logger` (nullable), `source` (file or `stdin`), `attributes` (dict), `raw` (original line). Unparseable lines become events with level `UNKNOWN` and a `parse_error` attribute — **never silently dropped** (count them in the report).

**Input formats:**
- **JSON-lines**: `{"ts": ..., "level": ..., "msg": ..., ...}` — accept common key aliases (`ts|timestamp|time`, `msg|message`, `logger|name`). Timestamps: ISO-8601 (with/without tz) and unix seconds/millis.
- **Plain text**: common patterns like `2026-01-15 08:23:01,441 ERROR [worker] Connection refused` — implement ≥ 3 configurable regex patterns; auto-detect format per file (probe first 10 lines).

## 5. Rule engine (built-in rules, each with named tests)

| Rule | Config (defaults) | Detects |
|---|---|---|
| `error_rate_spike` | window=5m, threshold=10% AND ≥ 20 events | error-level ratio above threshold in a window |
| `repeated_error` | min_count=5, window=10m | same normalized message (template, numbers wild-carded) repeating |
| `latency_outlier` | attr=`latency_ms`, p95 multiplier=5.0 | attribute above p95 × multiplier (JSON logs only) |
| `burst` | min_events=50, window=60s | event rate spike regardless of level |
| `level_gap` | — | CRITICAL events with no preceding WARNING from same logger (escalation without warning) |

- Rules implement a `Rule` protocol: `name`, `configure(RuleConfig)`, `evaluate(window) -> list[Incident]`.
- `Incident`: rule name, severity (`info|warn|critical`), first/last timestamp, affected event ids, human-readable summary, suggested action (one sentence, from rule metadata).
- A **config file** (TOML or JSON, `--config`) can enable/disable rules and override thresholds; invalid config = clean error with file+line, exit code 2.
- Scoring: report includes overall `health_score` (0–100) — deterministic formula documented in README (e.g., penalize incidents weighted by severity and event volume).

## 6. CLI contract

```
loglens parse   <input>                       # normalize + print table (or --format json)
loglens report  <input...> [--out report.html|--format terminal|json|html] [--config x]
                                              # multiple inputs: files, globs, or '-' for stdin
loglens watch   <input> --interval 5          # re-run report loop until Ctrl-C (read file growth)
loglens sample  [--events 5000] [--dir ./samples]   # generate demo logs (mixed formats, planted incidents)
```

- Exit codes: `0` success, `1` incident critical found (useful for CI), `2` usage/config error, `3` I/O error.
- `report --format html` writes a **single self-contained file** (inline CSS/JS, no CDN) with: summary cards (events, time range, health score), incidents table, error-rate sparkline (SVG), top messages table. Terminal output uses `rich` tables.
- All commands support `--since`/`--until` (relative like `30m` or ISO) filtering.

## 7. Sample data (planted anomalies)

`loglens sample` must generate data containing exactly these planted scenarios, and the built-in rules **must detect them on the sample** (this is the SMOKE_CHECK):
1. A 5-minute window with 30% error rate.
2. The same connection error repeated 12× in 8 minutes.
3. Latency p95 ≈ 120ms with outliers ≈ 4,000ms.
4. A CRITICAL from `payments` logger with no preceding WARNING.

Include the generated files in `samples/` in the README quickstart so the grader runs: `loglens report samples/app.log --out report.html`.

## 8. Testing requirements

- Unit tests per module; property-style tests for the parser over ≥ 50 malformed lines (documented fixtures in `tests/data/`).
- CLI tests via `typer.testing.CliRunner`: exit codes, `--help` for every command, report file creation, config error handling.
- Rule tests with fixed injected clock — every rule has a positive AND negative test.
- Streaming test: engine over a 100k-line generator uses O(1) events retained (assert via counting processed vs. held).
- Coverage ≥ 75% on `loglens/` (pytest-cov). Zero ruff warnings.
